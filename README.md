# SentimentPulse

A customer-sentiment analytics dashboard built as a college engineering project.
It reads customer reviews from a **SQLite** database, scores them with a transparent
**word list (lexicon)**, finds **unusually negative weeks/months** with simple statistics,
and shows **which complaint categories** appear in the negative reviews of those periods.

> **No AI model is used.** There is no LLM, no machine-learning model, no paid service
> and no API key. Every number and every sentence on the dashboard is computed from the
> review data by ordinary code you can read.
>
> **The included data is synthetic.** `data/reviews.db` is generated by
> `scripts/generate_data.py`. The reviews are made up; the "bad period" in May 2026 never
> happened. The dashboard says so on every page.

---

## 1. Problem statement and objectives

A company with thousands of reviews cannot read them all. SentimentPulse answers five questions:

1. What is the overall customer sentiment?
2. How has sentiment changed over time?
3. When did unusually negative sentiment occur?
4. What were customers complaining about in those periods?
5. What recurring issues appear alongside the drop in sentiment?

## 2. Technologies

| Part | Technology | Why |
|---|---|---|
| Data store | SQLite (`sqlite3`) | One file, no server |
| Analysis | Python 3 **standard library only** (`re`, `collections`, `json`, `datetime`, `unittest`) | Nothing to install; easy to explain |
| Front end | HTML, CSS, plain JavaScript, **D3.js 7.9** (bundled in `public/js/vendor/`) | Interactive charts, works offline, no framework |
| Hosting | Any static host (Vercel planned) | The site is only files; no server runs Python |

## 3. How the pieces connect

```
scripts/generate_data.py ──► data/reviews.db            (sample data; replace with your own)
                                   │
backend/main.py:  read ─► score ─► aggregate ─► outliers ─► complaints ─► write JSON
        ▲                                                                     │
 backend/lexicon.py                                                           ▼
 (+ optional data/custom_lexicon.json)                          public/data/*.json  (8 files)
                                                                              │
                                              public/index.html + js/*.js: fetch ─► D3 charts
```

The **only link between Python and the browser is the JSON files**. Python does all the
statistics once; the browser just displays them (it re-scores text only in the live analyzer).

## 4. Setup and running

You need **Python 3** (developed and tested on 3.13; other recent 3.x versions should work but were not tested). There is nothing to install: `requirements.txt`
is intentionally empty of packages.

```bash
# 1. (optional) rebuild the sample database - the same seed always gives the same data
python scripts/generate_data.py

# 2. run the analysis pipeline: reads data/reviews.db, writes public/data/*.json
python backend/main.py

# 3. run the tests
python -m unittest discover -s tests

# 4. view the dashboard (a local web server is required; double-clicking index.html will not work
#    because browsers block fetch() on file:// pages)
python -m http.server -d public 8000
#    then open http://localhost:8000      (on Windows use  py  instead of  python  if needed)
```

### Regenerating the JSON data

Run `python backend/main.py` any time the database or the lexicon changes. It overwrites the
8 files in `public/data/`. Options:

```
python backend/main.py --db other.db --out public/data
python backend/main.py --db other.db --table comments --date-col created_at --text-col body
python backend/main.py --lexicon data/custom_lexicon.json
```

### Using your own database

Provide a SQLite file with a table like this (column names can be changed with the options above):

```sql
CREATE TABLE reviews (
  id          INTEGER PRIMARY KEY,
  review_date TEXT NOT NULL,   -- 'YYYY-MM-DD' or 'YYYY-MM-DD HH:MM:SS'
  review_text TEXT NOT NULL
);
```

Rows whose date cannot be read, or whose text is missing, are skipped and counted
(`skipped_rows` in `meta.json`, shown in the page footer). Optionally add a table
`dataset_info(key, value)` with keys `name`, `is_synthetic` (`true`/`false`) and `notice`
to label the dataset on the dashboard. Without it, the dataset is treated as real data and no
"synthetic" banner is shown, so **do not** feed synthetic data without that label.

## 5. The data contract (8 JSON files in `public/data/`)

Every file has `"schema_version": 1`, UTF-8 text, ISO dates, and `null` (never `0`) for values
that do not exist. Week/month ids are produced only by Python.

| File | Contents |
|---|---|
| `meta.json` | dataset name and synthetic flag, date range, method settings (thresholds), lexicon version, skipped rows |
| `summary.json` | KPIs: totals, positive/negative/neutral counts and %, overall average, outlier counts |
| `timeseries.json` | `week[]` and `month[]`: one entry per period **including empty ones** (count, average, class counts, previous-period comparison, outlier flag) |
| `outliers.json` | per granularity: status, baseline mean/std, flagged periods with z-score, severity and a plain-English reason |
| `reviews.json` | every review once: score, class, matched words, complaint categories, `week` and `month` ids |
| `complaints.json` | category list, whole-dataset block, and one block per week/month (counts, %, example review ids, explanation text) |
| `lexicon.json` | the word lists used, a version fingerprint, complaint keyword groups |
| `parity_cases.json` | copy of `data/parity_cases.json` for the Python/JavaScript parity test |

Clicking a chart point works by id: the point's period id (`2026-W21`) selects the reviews whose
`week` field equals that id, so the chart and the review list always come from the same records.

## 6. Methodology

### 6.1 Lexicon-based sentiment scoring
Each review is lowercased and split into words with the pattern `[a-z]+(?:'[a-z]+)?` (curly
apostrophes are normalised first). Every word in the **positive** list adds 1; every word in the
**negative** list subtracts 1:

```
score = positive matches − negative matches
```

Score > 0 is *positive*, < 0 *negative*, = 0 *neutral*. Matching is by whole word, so "slowly" does not
match "slow", and a repeated word counts every time. Example from the specification:
"The delivery was slow but the product was excellent." → +1 (excellent) − 1 (slow) = **0**.

**Python and JavaScript use the same tokenizer and rules.** They are checked against each other
with 29 hand-written cases (`data/parity_cases.json`) and, in the dashboard itself, by re-scoring every
review in the browser and comparing with Python's result (shown under the Live analyzer).

### 6.2 Weekly and monthly aggregation
* Weeks are **ISO 8601 weeks (Monday start)**, id `YYYY-Www`; months are calendar months, id `YYYY-MM`.
* A period's value is the mean score of the reviews in it.
* Periods are generated continuously from the first to the last date, so a week with no reviews
  is a **gap** (`avg_score: null`) and is never treated as zero.
* Each period is compared with the **nearest earlier period that has data**; the comparison says when
  there was a gap in between.
* Overall figures use all reviews directly (review-weighted). They are never an average of period averages.

### 6.3 Negative outlier detection (z-score)
1. Only periods with enough reviews are eligible: **≥ 8** (weeks) or **≥ 20** (months).
2. At least **6** eligible periods are needed, otherwise the status is `insufficient_data`.
3. The mean and sample standard deviation of the eligible period averages form the baseline.
4. `z = (period average − mean) / std`. A period is flagged if **z ≤ −1.5**; it is *severe* if z ≤ −2.0, otherwise *moderate*.

Why these numbers: with *n* periods the largest possible |z| is (n−1)/√n, which is only 1.79 for n = 5,
so a stricter threshold could never fire on small data. Weeks and months are tested separately.

**Weakness (masking):** a very bad period raises the standard deviation, which can hide a milder one.
A flagged period means *unusually low compared with the rest of the data*. It is **not** proof of an
outage or of any cause.

### 6.4 Complaint categorisation
Only **negative** reviews (score < 0) are analysed. Keyword groups in `backend/lexicon.py` (delivery,
quality, support, pricing, website, returns) match whole words or phrases (a trailing `*` means "any ending",
e.g. `refund*`). A negative review matching none goes to *other*. For each period:

* a category counts **distinct reviews** that mention it (a review repeating "late" three times counts once);
* one review may belong to several categories, so percentages can add up to more than 100 %;
* percentage = reviews in category ÷ negative reviews in the period;
* with fewer than **5** negative reviews the dashboard says the evidence is insufficient.

### 6.5 Evidence-based explanation
The explanation is a fill-in-the-blanks template. It names at most 3 categories, only those found in
**at least 2** reviews, with their real counts and percentages, and always states that this is
*association reported by customers*, not a verified technical cause. The same data always produces the same text.

### 6.6 Four ideas that are easy to confuse
* **Lexicon sentiment analysis**: counting known positive/negative words to score *one review*.
* **Statistical outlier detection**: asking whether a *whole period's average* is unusually low compared with the other periods.
* **Complaint categorisation**: sorting *negative reviews* into topics using keywords.
* **Evidence-based explanation**: a template that reports the counts found, with caveats, and claims nothing more.

## 7. Dashboard features

* KPI cards (total, positive/negative/neutral with %, average score, outlier count) and a sentiment-mix bar.
* Interactive D3 trend chart: weekly/monthly toggle, zero baseline, green/red treatment, tooltips,
  outlier rings, hollow points for periods with too few reviews, dashed bands for empty periods, keyboard support.
* **Click a point** → period inspector: stats, comparison with the previous period, why it was flagged, complaint
  explanation, complaint bar chart (click a bar to filter), example reviews per category, and the **original reviews**
  of that period with scores and highlighted matched words.
* Review explorer: search, sentiment/category/period filters, sorting, pagination, click a row for details.
* Editable lexicon (add/remove words, no duplicates, export JSON) and live review analyzer.
* Review text is always inserted as plain text (never `innerHTML`), so HTML or script inside a review is shown, not run.

### Editing the lexicon
Edits made in the browser stay in **that browser** (localStorage) and affect only the Live analyzer. They do
**not** change the dashboard figures or the Python backend. To apply a change for real: click *Export lexicon*,
save the file as `data/custom_lexicon.json`, and run `python backend/main.py`.

The website is the `public/` folder; no Python or database runs in production. The planned host is **Vercel**:
import the repository, set the *Output Directory* to `public`, leave the build command empty, and commit the
generated `public/data/*.json`. Re-run `python backend/main.py` locally and commit before each deploy.

## 10. Limitations and future work

* No negation, sarcasm, slang or other languages: "not good" scores **+1**. A few synthetic reviews show this on purpose.
* Reviews scoring exactly 0 (including mixed reviews) are neutral and are not part of the complaint analysis.
* Keyword categories are simple and miss unusual wording; those reviews appear under "other".
* Weeks at the start/end of the data can be partial and have few reviews.
* Mean/standard-deviation detection can be masked by one very bad period (see 6.3); median/MAD would be more robust but harder to explain.
* The deployed site is a snapshot; it updates only when the pipeline is re-run and the files are redeployed.
* Ideas: negation handling, weighting words by intensity, phrase lexicons, trend forecasting, scheduled pipeline runs.

## 11. Demonstrating it to a panel (about 5 minutes)

1. Overview: 883 synthetic reviews; point out the "synthetic data" banner and the KPI cards.
2. Trend chart: the dip in May is ringed in red; hover for the tooltip; note the dashed gap (no data ≠ zero).
3. Click the worst week: show the z-score reason, the complaint explanation and the bar chart; click the "Delivery" bar and read the real reviews.
4. Switch to Monthly: May is flagged there too, independently.
5. Live analyzer: type the specification's example (score 0), then edit the lexicon and show the result change.
6. Explain the limits honestly: try "Not good at all." (+1) and explain why a lexicon cannot handle negation.
